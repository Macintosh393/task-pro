## Правила використання UI-kit

UI-kit — спільна основа інтерфейсу. Правила описують загальний підхід до розробки й не адресовані конкретним учасникам команди.

Важливо розрізняти спільні UI-компоненти та компоненти функціональності застосунку. `Button`, `Input` і `Modal` належать до `frontend/src/components/ui`. `TaskCard`, `BoardHeader` і `CreateBoardForm` розміщуються поза `ui`, у відповідних папках функціональності: вони поєднують UI-компоненти та реалізують поведінку продукту.

1. **Насамперед використовувати UI-kit.**

   Складніші компоненти потрібно будувати з наявних UI-компонентів. Нативні семантичні елементи та обгортки для компонування — наприклад, `section`, `form` і `div` — дозволені. Не слід повторно реалізовувати елементи керування, які вже є в UI-kit.

2. **Зберігати спільні UI-компоненти в `ui`.**

   Повторно використовувані візуальні елементи керування належать до UI-kit. Компоненти окремої функціональності та бізнес-логіка — до відповідних папок функціональності. Не слід створювати довільні компоненти без чіткого призначення та місця в структурі проєкту.

3. **Обговорювати відсутні можливості перед створенням нової абстракції.**

   Спочатку потрібно перевірити, чи можна задовольнити потребу поєднанням наявних компонентів або їхнім поточним API. Якщо потрібен новий спільний компонент, слід узгодити його призначення та API, а потім додати до `ui`.

4. **Усувати розбіжності з дизайном на рівні компонента.**

   Потрібно вказати розбіжність і відповідне джерело в дизайні. Якщо виправлення стосується всіх використань — оновити наявний компонент. Якщо обидва оформлення потрібні — додати варіант. Якщо відрізняються призначення або поведінка — створити окремий компонент у `ui`. Навмисні відхилення від дизайну потрібно документувати.

5. **Уникати локальних обхідних рішень у стилях.**

   Код окремої функціональності не повинен перевизначати внутрішні CSS-селектори, кольори чи розміри UI-компонента, щоб імітувати інший варіант дизайну. Повторно використовувані візуальні відмінності мають бути частиною API компонента. Розміщення, відступи між компонентами та доступна ширина можуть визначатися там, де компонент використовується.

6. **Не оголошувати компоненти всередині інших компонентів.**

   Функції компонентів потрібно оголошувати на рівні модуля. Звичайне компонування JSX, умовний рендеринг, обробники подій і функції зворотного виклику для рендерингу дозволені. В окремий компонент варто виділяти повторювану або самостійно змістовну частину інтерфейсу, а не кожну обгортку.

7. **Робити UI-компоненти самодостатніми та незалежними від бізнес-логіки.**

   Кожен UI-компонент має власну папку з реалізацією, стилями, історіями Storybook, потрібними тестами та допоміжними файлами. Дані та обробники передаються через props. UI-компонент не повинен знати про API задач, автентифікацію чи маршрути застосунку.

8. **Робити зміни спільних компонентів зрозумілими для перевірки.**

   Потрібно підтримувати документацію props і змістовні стани у Storybook. Перед зміною спільної поведінки слід перевірити відповідні теми, адаптивність і наявні місця використання. Не слід створювати майже однакові компоненти лише для обходу питань сумісності.

Папка `ui` має залишатися набором повторно використовуваних компонентів, а не містити весь застосунок. Детальні контракти, структура та приклади описані в [документації UI-kit](frontend/docs/ui-kit.md).
