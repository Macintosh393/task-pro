# Tech Stack

## Frontend

| Параметр | Значення |
| --- | --- |
| Фреймворк | React із TypeScript |
| Стан застосунку | Локальний React state та Context для спільного стану |
| Маршрутизація | React Router — пропозиція з попереднього плану, остаточне рішення ще потрібно підтвердити |
| Стилізація | Tailwind CSS та CSS custom properties для тем |
| Збірка | Vite |

Чому обрали:

- **React і TypeScript:** компонентний підхід підходить для повторюваних елементів TaskPro — дошок, колонок, карток і форм. Типізація допоможе узгодити props та структури даних під час спільної розробки.
- **Локальний state і Context:** для простого застосунку з особистими дошками починаємо зі вбудованих засобів React. Локальний стан відповідає за окремі компоненти, Context — за стан, який потрібен у кількох частинах інтерфейсу. Це зменшує кількість інструментів, які команда має освоїти одночасно.
- **React Router:** запропонований для навігації між сторінками входу, реєстрації та дошками. Підхід до маршрутів ще треба погодити.
- **Tailwind CSS і CSS custom properties:** утиліти допомагають оформлювати компоненти, а спільні змінні кольорів — підтримувати Light, Dark і Violet без дублювання компонентів для кожної теми.
- **Vite:** забезпечує локальний dev server і production build React-застосунку. У development frontend і NestJS запускаються окремо; у production NestJS віддаватиме зібраний frontend разом з API.
- **Storybook і Vitest:** Storybook обрано для ізольованої розробки та перегляду UI-компонентів, Vitest — для frontend-тестів. React Testing Library не використовуємо; конкретний підхід до тестування взаємодій React-компонентів ще потрібно погодити.

## Backend

| Параметр | Значення |
| --- | --- |
| Мова | TypeScript; середовище виконання Node.js |
| Фреймворк | NestJS |
| База даних | PostgreSQL |
| ORM / драйвер | TypeORM |
| Автентифікація | Власна email/password; JWT у HttpOnly/Secure cookies, хеші refresh-токенів у PostgreSQL; logout відкликає відповідний refresh-токен і очищає cookies |
| Документація API | Специфікація OpenAPI та інтерактивна документація Swagger UI |

Чому обрали:

- **TypeScript і Node.js:** спільна мова для frontend і backend дозволяє обом full-stack учасникам працювати з обома частинами застосунку. Типізація допомагає описувати API та моделі даних.
- **NestJS:** модулі, controllers і services дають зрозумілу структуру для автентифікації, користувачів, дошок, колонок і карток. NestJS також слугуватиме сервером API та зібраного frontend у production.
- **PostgreSQL:** реляційна модель відповідає зв'язкам між користувачами, їхніми дошками, колонками та картками й дозволяє контролювати цілісність даних.
- **TypeORM:** дає змогу описувати сутності та зв'язки в TypeScript і керувати змінами схеми через migrations. Правила видалення та впорядкування погоджуватимемо перед відповідними функціями.
- **Власна email/password автентифікація та JWT:** відповідають потрібним сценаріям реєстрації та входу. Паролі хешуємо, доступ до особистих даних перевіряємо за власником. Токени передаємо через HttpOnly/Secure cookies; PostgreSQL зберігає хеші refresh-токенів, а не їх відкриті значення. Logout відкликає відповідний refresh-токен і очищає cookies. Access JWT мають бути короткоживучими: без окремої перевірки відкликання вже виданий stateless access JWT залишається чинним до завершення строку дії. Точні строки життя та потребу в негайному відкликанні access JWT ще погоджуємо. Для cookie-автентифікації потрібні відповідна політика SameSite і захист від CSRF; конкретний режим та механізм визначимо перед реалізацією.
- **OpenAPI та Swagger UI:** OpenAPI обрано для специфікації endpoint-ів, форматів запитів і відповідей, а Swagger UI — для інтерактивного перегляду цієї документації. Це дає frontend і backend узгоджений API-контракт для інтеграції.

## Інфраструктура

| Параметр | Значення |
| --- | --- |
| Хостинг frontend | AWS; зібраний frontend віддаватиме NestJS. Конкретний сервіс ще не обрано |
| Хостинг backend | AWS; NestJS API та production frontend в одному застосунку. Конкретний сервіс і розміщення PostgreSQL ще не обрані |
| Хмарне сховище | Не визначено. Перед реалізацією avatar потрібно уточнити вимогу до Cloudinary; AWS storage не обрано як заміну |

## Знання команди

Що знаємо добре:

- За початковим командним TECH.md, база команди — JavaScript, HTML і CSS; є знайомство з Node.js/Express, HTTP/REST та основами реляційних баз даних. Це вихідна самооцінка, а не підтвердження однакового рівня кожного учасника.
- Влад бере на себе технічну координацію, review та AWS/DevOps. Двоє інших учасників розвиваються як full-stack розробники; постійного поділу на frontend і backend немає.

Що вчимо по ходу:

- **React і TypeScript:** компоненти, props, hooks, типізацію та розподіл локального і спільного стану через Context.
- **Tailwind CSS і теми:** повторне використання стилів, semantic CSS variables і три теми інтерфейсу.
- **Storybook і Vitest:** ізольовану розробку UI, stories та змістовні frontend-тести без React Testing Library.
- **NestJS, PostgreSQL і TypeORM:** модулі, dependency injection, API, зв'язки даних, migrations, валідацію та перевірку власника ресурсів.
- **Автентифікацію й тестування backend:** безпечне зберігання паролів, життєвий цикл сесії/токенів і перевірку помилкових сценаріїв. Backend test tooling та метрики coverage ще треба погодити; ціль проєкту — щонайменше 70% backend coverage.
- **Конфігурацію та deployment:** npm scripts, спільну Node.js LTS, ESLint/Prettier, локальний запуск і production build. Точну Node LTS ще потрібно обрати. Застосунки спочатку запускаємо локально; мінімальний PostgreSQL Compose додаємо на етапі БД, контейнеризацію застосунків — пізніше. AWS/DevOps веде Влад.

Як закриємо прогалини:

- Використовуємо університетські курси React і NestJS, офіційну документацію обраних інструментів та [курс Storybook від Steve Kinney](https://stevekinney.com/courses/storybook).
- Обидва учасники практикують frontend і backend в окремих навчальних гілках. Спільні зміни робимо невеликими PR з одним відповідальним і review іншого учасника.
- Конфігурації створюємо з нуля зрозумілими кроками; автор пояснює призначення файлів, scripts і залежностей. Якщо використовуємо framework CLI, розбираємо та спрощуємо його результат.
- Щоб зменшити труднощі з UI та темами, розробляємо невеликі primitives у Storybook, використовуємо спільні semantic tokens і перевіряємо компоненти в усіх трьох темах.
- Щоб рано виявити проблеми інтеграції, погоджуємо формати API й перевіряємо зв'язок frontend/backend на простому health endpoint. UI-робота не повинна залежати від БД або AWS credentials.
- Перед реалізацією автентифікації, component-тестів і хмарної інфраструктури закриваємо відповідні відкриті рішення. Блокери обговорюємо з Владом, а неоднозначні вимоги завдання — з ментором.
